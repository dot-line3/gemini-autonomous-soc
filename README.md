# AI 자율 SOC 파이프라인 (Autonomous AI SOC Security Gateway)

메인 AI 서비스 앞단에서 프롬프트 인젝션, 탈옥(Jailbreak), 정보 유출 시도를 실시간으로 탐지·차단·정화하는 FastAPI 기반 비동기 보안 게이트웨이입니다.

## 🛡 방어 구조 (L0 → L1 → L2)

```
요청 → 블랙리스트 확인 → L0 정규식 사전 필터 → L1 Gemini 위협 스코어링 → L2 정화 → 메인 LLM
```

| 단계 | 역할 | 처리 |
|---|---|---|
| L0 | 명확한 악성 지시어를 API 호출 없이 즉시 차단 | 정규식 Fast-Block / 완전 일치 Fast-Pass |
| L1 | 문맥 기반 위협 점수(0.0~1.0) 산출 | Gemini + Pydantic 구조화 출력 |
| 판정 | Score ≥ 0.8 차단 + 블랙리스트 / 0.4 ≤ Score < 0.8 정화 / 그 외 통과 | `run_security_pipeline()` 공통 함수 |
| L2 | 악성 구문만 제거하고 사용자 의도 유지 | Gemini 정화 |

### 안정성 설계
- **3단계 모델 우회 체인**: `gemini-3.5-flash-lite → gemini-3.6-flash → gemini-3.1-flash-lite` (보안 판정 L1·L2, 메인 LLM 공통)
- **서킷 브레이커**: 429(할당량 초과)·응답 시간 초과가 난 모델은 일정 시간(에러의 재시도 시간, 기본 60초) 건너뛰고, 시간이 지나면 요청 1건으로 회복 여부를 확인한 뒤 원래 순서로 복귀. 404(제공 중단)는 1시간 건너뜀. 503은 1초 후 1회 재시도
- **호출 제한 시간**: L1 8초 / L2 12초. 모델이 응답 없이 멈춰도 다음 모델로 전환
- **Fail-Closed**: 모든 모델이 실패하면 검사되지 않은 요청을 통과시키지 않고 `503` 반환 (사용자는 차단하지 않음)
- **정화 결과 검증**: L2 정화기의 출력이 비어 있거나(EMPTY), 원문 그대로이거나(NOOP), 요청에 직접 답한 것(ANSWER: 코드 블록·여러 문단·과도한 길이)이면 통과시키지 않고 `403` 차단
- **응답 검증**: 빈 응답·잘린 JSON을 감지해 다음 모델로 전환, 원인은 `soc_debug.log`에 기록
- **스트리밍 중복 방지**: 출력 도중 실패하면 다른 모델로 처음부터 다시 생성하지 않음

## 🔧 개발 중 해결한 문제
- **429 재시도 낭비 → 서킷 브레이커**: 직접 벤치마크를 돌리다 1순위 모델이 할당량 초과 중인데도 요청마다 "시도 → 429 → 1초 대기 → 재시도 → 429"를 반복하는 것을 로그로 확인. 429가 난 모델을 일정 시간 건너뛰는 서킷 브레이커 도입
- **제공 중단 모델(404)**: 3순위 `gemini-2.5-flash-lite`가 "no longer available to new users"로 막혀 체인이 사실상 2단계였음. `check_models.py`로 후보 모델을 실제 호출해 확인 후 `gemini-3.6-flash`로 교체 (메인 LLM 체인도 동일)
- **응답 멈춤**: 모델이 응답 없이 멈추면 L1도 함께 멈추는 구조 → 호출 제한 시간과 시간 초과 시 서킷 차단 추가
- **L2 정화기의 세 가지 실패**: 같은 요청에도 실행마다 ① 원문을 그대로 돌려주거나 ② 무해하게 고쳐 쓰거나 ③ 요청에 직접 답변(카드번호 생성 코드)함. 보안 계층의 AI 출력도 그대로 믿지 않도록 정화 결과 검증(EMPTY/NOOP/ANSWER → 차단) 추가
- **503 오진**: 초기에 정상 질문 25건 중 9건이 차단되어 필터가 너무 엄격한 줄 알았으나, 원인을 추적해 무료 모델의 503 과부하로 보안 검사 자체가 실패한 것임을 확인 → 모델 우회 체인과 Fail-Closed 설계의 출발점
- **L0 오탐**: 정상 질문("레시피 추천")을 영구 차단하던 정규식 패턴을 벤치마크로 발견해 제거
- **Fail-Open 취약점**: API 장애 시 위협 점수 0.0으로 통과시키던 구조를 Fail-Closed로 변경
- **판정 누락**: 출력 토큰 한도·생각(thinking) 토큰으로 JSON이 잘리던 문제를 로그로 추적해 모델별 thinking 설정과 응답 검증 추가
- **벤치마크 오염**: 이전 실행의 블랙리스트가 다음 측정에 섞이던 문제를 실행별 고유 ID로 해결

## 🚀 실행 방법

```bash
python -m venv socvenv
socvenv\Scripts\activate          # macOS/Linux: source socvenv/bin/activate
pip install -r requirements.txt
```

`.env` 파일 생성:
```
GEMINI_API_KEY=your_gemini_api_key
```

```bash
python -m uvicorn main:app --reload    # 게이트웨이 실행 (http://127.0.0.1:8000)
python test.py                          # 튜닝셋 100건 벤치마크 (다른 터미널에서)
python test_holdout.py                  # Holdout 검증 (결과 파일이 있으면 재실행 차단, --force로만 재실행)
python test_external_redteam.py         # 외부 레드팀 검증 (동일)
python check_models.py                  # 후보 모델이 지금 이 API 키로 실제 응답하는지 점검
```

## ⚠️ 알려진 한계
- 서킷 브레이커 상태가 프로세스 메모리에 있어 여러 워커로 실행하면 워커마다 따로 관리됨 (Redis 등 공유 저장소 필요)
- 메인 LLM 응답 체인에는 서킷 브레이커·호출 제한 시간이 아직 없음
- 무료 API 할당량·혼잡도에 따라 지연 수치가 측정마다 크게 달라짐 (위 개선 과정 표 참고)
- `user_id`를 클라이언트가 전달하므로 위조 가능 (API 키/JWT 인증 연동 필요)
- `/admin/reset-db` 엔드포인트에 인증 없음 (로컬 개발용)
- 블랙리스트 해제 절차 없음, async 엔드포인트에서 동기 SQLite 사용
